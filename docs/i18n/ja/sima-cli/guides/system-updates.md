# システム更新の操作

`sima-cli update` で日次ビルド、署名済み eLxr 3.0 SWU バンドル、A/B 検査、ストレージへのステージング、永続オーバーレイの処理を利用します。

コマンドリファレンス: [`sima-cli update`](../../../../sima-cli/commands/sima-cli-update.md)

## eLxr 3.0+ の内部日次更新

内部モードではプレリリースの警告を表示します。eLxr 3.0+ を実行中の Modalix デバイスでは、`sima-cli -i update` はまず Artifactory を照会します。認証情報の欠落、HTTP 401/403 または 5xx 応答、接続失敗、タイムアウトの場合は、[日次プラットフォームインデックス](https://artifacts.neat.sima.ai/daily-platform-images/index.json)へフォールバックします。照会に成功して一致するビルドがない場合はフォールバックしません。

```bash
sima-cli -i update -f -v 3.0
sima-cli -i update -f -v 3.0.0_daily_develop_B1247
```

完全一致が優先されます。部分検索はインデックスを絞り込み、一致結果を新しい順に表示します。palette SWU を含むビルドのみが対象です。ミラーからのダウンロードでは、署名付きインストールの前にインデックスのサイズと SHA-256 を検証します。`-f` がある場合、Artifactory のアーティファクトダウンロードの失敗時には、選択済みの同じビルドだけにフォールバックできます。アーティファクトの欠落や整合性検査の失敗はインストール前に停止します。

eLxr 2.1.3 のデバイスは従来の APT 更新動作と `--force` ポリシーを維持します。これらを 3.0 に移行するには復旧またはプロビジョニングが必要です。

## eLxr 3.0 の署名済み A/B 更新

A/B がプロビジョニング済みの Modalix システムでは、`update` は実行中のスロットと `/data` を保持し、非アクティブスロットに署名済みの全システム SWU をインストールします。

```bash
sima-cli update /path/to/full-system.swu
sima-cli update --ip 192.168.6.5 /path/to/full-system.swu
sima-cli update --inspect
sima-cli update --ip 192.168.6.5 --inspect
```

ステージングは `/data`、`/media/nvme/swupdate`、`/tmp` の順に確認し、バンドルに加えて 64 MiB の余裕が必要です。SWUpdate は `/tmp` に展開用の容量も必要です。`/tmp` が RAM 上にある場合、`df` が十分な容量を示していても利用可能な RAM を確認します。専用 tmpfs は、512 MiB または RAM の 10% の大きい方をシステム用に残せる場合にのみ、現在のマウントで拡張できます。`--dryrun` はマウントを変更せず実行可能な拡張を報告します。

`--dryrun` を除き、使用前に NVMe を読み書き可能でマウントまたは再マウントします。ダウンロードしたバンドルと一時ステージングはインストール成功直後に削除します。失敗した場合は診断のためステージング済みバンドルを保持し、ユーザーが提供した元ファイルは削除しません。

リモート更新はホストでダウンロードし、選択したボードのストレージへ転送し、転送のチェックサムを検証して、ボードで SWUpdate を実行します。ローカルとリモートの両モードは署名済みバンドルを検証し、`update,full` を選択します。`/etc/swupdate/public.pem` がなければ同梱の SiMa 証明書を一時的に配置し、後で削除します。既存の鍵は保持します。`--force` はミラーへのフォールバックだけを変更し、署名検証を無効にしません。

インストール成功後は再起動が必要です。`--reboot` を指定したリモート更新は再接続し、新しいスロットと正常性の確認を検証します。接続の切断やインストール失敗は、再試行する前に調べてください。

## A/B の検査

`--inspect` は両スロット、バージョンと有効性、実行中と次回起動のスロット、保留中の更新とロールバックの状態、起動回数を表示します。ファームウェアのダウンロードやインストール、スロット切り替え、再起動、sima-cli の自己更新は行いません。

永続オーバーレイのイメージでは、基盤デバイスを検証した後、`/oldroot` の未変更のルートから稼働中のバージョンを読み取ります。必要ならジャーナルの再生を無効にしてもう一方のルートを一時的に読み取り専用でマウントし、以前の LVM の有効化状態を復元します。欠落した、または検証できないメタデータは不明のままです。

## 永続オーバーレイのカスタマイズの処理

検査と通常の 3.0 更新は、読み取り専用のオーバーレイ概要を表示します。レポートは実際に適用されている dpkg データベースと下位層のデータベースを比較し、上位層の項目を設定/サービス、ローカルソフトウェアの候補、削除、パッケージ状態、キャッシュ/ログ、その他のファイルに分類します。`--verbose` は全パッケージの比較と分類ごとの件数を追加します。

`simaai-palette-*` が異なるパッケージセットのビルド ID を示す場合、sima-cli は永続メタデータが以前のイメージのものであり、APT が誤ったバージョンを報告したりイメージとオーバーレイのファイルを混在させたりする可能性を警告します。上位層へコピーされたファイルは意図的なカスタマイズと自動分類せず、利用できない、または読み取れない基準データは推測せず報告します。

更新中にパッケージビルドの不一致があると、オーバーレイをクリーンにするワークフローを提示します:

1. 選択した SWU が `SWUPDATE_CLEAN_OVERLAY` をサポートすることを検証します。
2. `/data/.overlay-backup` に一覧を保存し、チェックサムを作成します。
3. オーバーレイのクリーンアップを有効にして SWUpdate を実行します。
4. 再起動後の検証と再インストールの手順を表示します。

`-y` があれば、不一致の検出時にクリーンアップを自動選択します。`-y` がなければ、ユーザーはオーバーレイを保持できます。クリーンアップ契約のないバンドルはインストールやバックアップの前に拒否します。一覧はパッケージ選択、イメージの識別情報、パス、所有権、権限を記録しますが、ファイル内容、dpkg データベース、APT キャッシュ、上位層全体は含みません。これは復旧情報であり、自動復元アーカイブではありません。リモート DevKit でも `--ip` で同じワークフローを利用できます。
